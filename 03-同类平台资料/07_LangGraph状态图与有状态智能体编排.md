# LangGraph：状态图与有状态智能体编排

资料来源：GitHub 仓库 langchain-ai/langgraph 的 README.md，仓库地址 https://github.com/langchain-ai/langgraph 。抓取日期 2026 年 11 月 12 日，当时仓库星标约 4.5 万。本文依据原始 README 整理为中文，保留项目自述的术语与能力划分。

## 一、项目定位

README 把 LangGraph 定义为「用于构建有状态智能体的低层编排框架」，并强调它是低层支撑设施，适用于任何长时间运行、带状态的工作流或智能体。它不是拖拽式画布产品，而是供开发者以代码方式描述状态、节点与边的框架。README 同时提到 Klarna、Replit、Elastic 等公司在使用它，并给出安装方式 pip install -U langgraph。

之所以强调「低层」，是因为它把编排的骨架交给开发者：状态如何定义、节点如何更新状态、边在什么条件下跳转，都由代码控制。与之相对，可视化工作流平台把同样的骨架做成画布上的节点与连线，让使用者不必直接写编排代码。

## 二、README 列出的五项能力

**1. 持久化执行 Durable execution**。智能体能够在故障中保持状态并长时间运行，恢复时从离开的位置自动继续，而不是从头重跑。

**2. 人在回路 Human-in-the-loop**。执行过程中可以随时检查并修改智能体状态，把人工监督嵌进流程。

**3. 完备的记忆 Comprehensive memory**。既包含支撑当前推理的短期工作记忆，也包含跨会话保存的长期记忆，使智能体真正具备状态。

**4. 借助 LangSmith 调试**。通过可视化工具追踪执行路径、记录状态迁移、采集运行时指标，从而看清复杂智能体行为。

**5. 生产级部署**。面向长时间运行、有状态工作流的特点提供可伸缩的部署基础设施。

## 三、与可视化工作流编排的对应关系

LangGraph 的「状态图」由状态、节点和边构成，条件边决定下一步走向，长时间运行依赖检查点保存状态。把这些概念映射到节点式画布上，大致对应变量系统、执行节点、条件判断节点与循环节点：变量在各节点之间传递并更新，条件判断决定分支，循环实现重复执行，运行记录承担追踪职责。

本平台采用固定输出变量并支持作用域嵌套，每个节点产出固定变量名、下游按名字引用；条件判断节点分出「是」与「否」两条边；循环节点对集合逐项调用子工作流并汇总结果；运行历史页面保留执行记录。这些都可以看作状态图思想在图形界面上的表达。差别在于 LangGraph 的可恢复执行与长期记忆依托其运行时与检查点机制，本平台则以本地 SQLite 保存工作流、运行历史与知识库分块，执行过程本身以单次运行为主。

## 四、生态系统

README 列出 LangGraph 周边的配套项目：Deep Agents 是构建在其上的高层包，面向具备规划、子智能体与文件系统使用能力的任务；LangChain 提供可组合组件与集成；LangSmith 用于评测与可观测性，可以调试表现不佳的运行、评估智能体轨迹；LangSmith Deployment 面向长时间运行的有状态工作流提供部署与复用，并支持在 LangSmith Studio 中做可视化原型。另有 LangGraph.js 作为 JavaScript 与 TypeScript 的对应实现。

## 五、答辩中可以说明的一点

把 LangGraph 与本平台并列，可以说明「工作流编排」有两个层面：一层是框架，用代码精确控制状态与恢复；另一层是工具，把同一套结构变成可拖拽的画布。本平台选择后者，并在画布里保留了条件分支、循环、并行、变量传递等足够表达流程逻辑的能力，同时把知识检索与模型节点作为可编排的一等节点纳入其中。
