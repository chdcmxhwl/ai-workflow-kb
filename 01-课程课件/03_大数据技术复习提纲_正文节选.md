# 大数据技术 期中复习提纲（正文节选）

一、这门课在学什么

课程内容分成两条主线。一条是 Hadoop 生态组件及其应用，这是基础设施层面的内容，涉及存储、计算、资源调度和一批周边工具。另一条是智能应用开发，建立在大模型、机器学习和深度学习之上，属于数据之上的应用层。

课程的落点是自己动手做出一个系统，课件给出了四类参考形态。用 HDFS 作为存储的云盘系统；用 HBase 作为数据库的云笔记；用 Hive、Spark 等技术完成的大数据分析与可视化系统；用大模型实现的智能系统，例如基于 RAG 架构与 RWKV 大语言模型的江西文旅智能导游，以及教育智能体开发。

这四类形态可以归成三个层次来记：存储用 HDFS 和 HBase，分析用 Hive 和 Spark，智能用大模型配合 RAG 与 RWKV。考试如果问课程目标，答出「掌握 Hadoop 生态组件及应用与智能应用开发技术，最终独立实现一个使用大数据技术的系统」这条主线即可，再举出上面任意一到两个例子作为佐证。

二、大数据分析流程

流程分四步，顺序不能颠倒。

1. 数据获取。 这一步回答数据从哪里来的问题。课件列举了三类主要来源：用爬虫抓取互联网上的数据，在网页或应用中埋点采集用户行为数据，通过传感器采集物理世界的数据。获取环节解决的是分析所需的原材料问题。

2. 数据预处理。 原始数据通常存在缺失、重复、异常和格式不统一的情况，需要清洗。缺失值填补、异常值处理、去重、单位与格式统一这些工作都在这个环节完成。

3. 数据分析（挖掘）。 在清洗之后的数据上做分析和挖掘，目标是找出有用的模式。课件把这一步概括为「分析及挖掘有用模式」，也就是说这一环节的产出不是报表，而是数据中隐藏的规律。

4. 数据应用。 把找出来的规律投入实际使用，典型形式包括推荐、识别和分类。

如果考到简述题，四步的名称加上每一步的主要工作就构成完整答案；如果考到举例说明，用下面推荐系统的例子把四步串一遍即可。

三、什么是 Hadoop

Hadoop 是一个共享存储分析系统，由两部分构成：HDFS 负责存储，MapReduce 负责分析计算。

这两部分的分工是理解整个生态的起点。HDFS 解决的是「海量数据放在哪里、怎么放才可靠」，MapReduce 解决的是「数据放在那里之后，怎么算才能算得完」。课件用一张图把 Hadoop 拆成「共享存储」和「共享分析」两块，两个箭头分别指向 HDFS 和 MapReduce。

这里有一个容易混淆的地方：Hadoop 不等同于 HDFS。HDFS 只是 Hadoop 的存储子系统，Hadoop 的完整含义还要包含计算框架，以及后来独立出来的集群资源管理系统 YARN。

四、Hadoop 与云计算的关系

课件指出，云计算的内涵比 Hadoop 更丰富，按照提供的服务差异可以分成三层。

1. IaaS，Infrastructure as a Service，基础设施即服务。 这一层属于硬件架构层，用户直接从大公司租用硬件基础设施，在其上搭建自己的云计算环境。课件的例子是 Amazon EC2。

2. PaaS，Platform as a Service，平台即服务。 这一层属于平台层面。Hadoop 就处在这一层，它是一种为云计算平台提供计算服务的平台。

3. SaaS，Software as a Service，软件即服务。 这一层属于软件服务层。课件特别提到，Hadoop 对于技术基础薄弱的使用者很难直接用起来，需要在平台之上再构建一些软件，才能方便一般人员使用，Salesforce 是这一层的代表。

结论是课件标红的那句话：Hadoop 仅是云计算中计算平台的一种实现方式。也就是说，云计算的范畴大于 Hadoop，Hadoop 只是其中一种 PaaS 层面的实现。回答「Hadoop 与云计算是什么关系」时，先讲三层服务的划分，再落到这句话上。

五、海量数据的存储需求

这一节是理解 HDFS 设计动机的钥匙，考「为什么 HDFS 要这样设计」这类题，答案基本都出自这里。

1. 数据量级

先记几个数量级，单位是 PB：

Google 在 2005 年收录 80 亿网页，2008 年日处理数据量超过 20PB；百度超过 200PB；Facebook 超过 100PB；Yahoo 超过 100PB；淘宝超过 15PB；中国电信云公司超过 30PB。

单位换算要会：1PB 等于 1024TB，1TB 等于 1024GB，因此 1PB 约等于 100 万 GB，200PB 大约是 20 万 TB。这类数字不要求精确背诵，但「这些公司的数据规模已经进入 PB 量级」这个结论必须清楚。

2. 环境特点

课件列了四条，每一条都直接对应 HDFS 的一项设计决策。

低成本。 硬件基础是大量相对廉价的计算机组成的集群，而不是昂贵的小型机或大型机，代价是单节点故障率较高。这条特点决定了 HDFS 必须在软件层面用冗余来兜底硬件不可靠，因此才有默认三副本和机架感知机制。

大文件。 系统中存放的是大量大尺寸文件，量级在 100MB 到 GB 级。这条特点决定了 HDFS 的块要设得比较大，同时决定了它不擅长应付海量小文件。

顺序读写。 数据的访问模式是顺序读写，极少随机读写，并且数据写入之后一般不再修改。这条特点决定了 HDFS 适合「一次写入、多次读取」的场景，也解释了为什么 HDFS 不允许随意修改文件中间的内容。

高吞吐量。 系统的整体目标是高吞吐量，而不是单次访问的低延迟。这解释了 HDFS 为什么宁可牺牲随机访问的性能，也要保证大批量数据连续读取时的整体效率。

这四条可以串成一句话来记：为了在便宜的机器上存下体量巨大的文件，HDFS 用大块切分、顺序读写、多副本冗余的方式，换取整体吞吐量和可靠性。

六、Hadoop 生态组件全景

课件第一页的生态图需要背下来，答题时按层次往上说。

1. 存储与资源层。 HDFS2 是分布式文件系统，位于整个体系的最底层，负责数据实际落地；YARN 是集群资源管理系统，负责把集群的 CPU、内存等计算资源分配给各个计算任务。

2. 计算框架层。 MapReduce 是分布式离线计算框架，面向批量数据；Tez 是 DAG 计算框架，把多个作业组织成有向无环图以提升执行效率；Storm 是流式计算框架，面向连续不断到来的数据流。

3. 数据仓库与数据挖掘层。 Hive 是数据仓库，可以用类 SQL 的方式查询存放在 HDFS 上的数据；Hive2 是它的后续版本。Pig 是数据流处理工具，用脚本的方式描述数据处理流程；Pig2 同理。Mahout 是数据挖掘库，内置了一批常用的机器学习算法。

4. 实时数据库层。 HBase 是建立在 HDFS 之上的实时分布式数据库，用来解决 HDFS 不支持随机读写和实时访问的短板。

5. 协作与管理层。 ZooKeeper 提供分布式协作服务，用于解决分布式环境中的一致性与协调问题；Ambari 是安装、部署、配置和管理工具，负责把这套组件装起来并管起来。

6. 数据采集与迁移层。 Flume 是日志收集工具，把分散在各处的日志汇聚起来写入存储系统；Sqoop 是数据库 ETL 工具，负责在关系型数据库与 HDFS 之间搬运数据。

如果觉得逐个记不住，可以抓位置：Ambari 在最上面统管全局，ZooKeeper 在一侧做协调，Flume 从外部把日志收进来，Sqoop 把数据库里的数据导出去，中间是 Hive、Pig、Mahout、HBase 这些直接面向使用者的数据服务，再往下是 MapReduce、Tez、Storm 三种计算框架，最底层压着 YARN 和 HDFS2。

回答「列举 Hadoop 生态的主要组件并说明作用」时，按层次组织比逐个罗列更容易拿分，因为分层本身说明你理解了它们之间的关系。

七、典型应用：电商推荐系统

课件第二页的推荐系统例子是综合分析题的常用素材，要能够讲清整条链路。

系统面向用户在首页看到的几个位置，包括热卖推荐、商品精选和猜你喜欢。用户在页面上的点击行为会被采集下来，作为后续推荐的输入。

1. 实时链路。 页面上的即时推荐要求响应快，课件给出的时间尺度是五分钟以内的数据。这条链路使用 Storm 或 Spark Streaming 处理，产出的是若干条推荐规则，直接作用于当前的页面展示。

2. 离线链路。 离线分析处理的是周期更长、规模更大的数据，课件给出的范围是最近一个月的数据。数据先经过 Pig 或 Hive 处理，再由 MapReduce 这个离线计算框架在 HDFS 上完成计算。参与计算的数据包括用户属性、商品属性，以及用户的点击、购买、收藏、加入购物车等行为记录。

3. 推荐算法。 算法部分由 Python 配合 Mahout 算法实现，也可以用 Spark MLlib。课件提到两类推荐思路，一类是基于物品的协同过滤，另一类是基于人口统计学的推荐。前者的依据是「买过某商品的人往往也会买另一件商品」，后者的依据是用户在年龄、性别、地域等属性上的相似性。

4. 输出结果。 最终的产出形式是一组形如「什么人、有过什么记录、推荐 A、B、C、D、E、F、G」的规则或清单，由前端消费并渲染到页面上。

这个例子最能体现大数据系统的两个特征：一条实时链路保证时效性，一条离线链路保证分析的深度和准确度，两条链路的结论最终汇聚到同一个推荐结果上。如果考到「设计一个大数据应用的基本架构」，把这里的结构迁移到其他场景即可，例如用 Flume 采集日志、用 HDFS 存储、用 Hive 或 Spark 分析、用 HBase 提供实时查询。

八、HDFS 的块机制与块大小选择

这一节是本讲的重点，也是概念题最容易失分的地方。课件另有三页按顺序展开写入过程——先拆分、再分配、最后给出分配所依据的机架感知策略，这一节把它们一并纳入，放在概念之后、权衡之前。

1. 什么是块

HDFS 把文件切分成若干个固定大小的数据块，每个块分别存放在不同的 DataNode 上。这样做的好处有两点：单个文件的大小不再受一台机器磁盘容量的限制；同一个文件的不同部分可以从多台机器上并行读取，从而提升整体吞吐量。

2. 文件写入时的拆分过程

课件用一幅四格图讲清了写入的起点。用户提出「给我写 200MB 数据」的请求，客户端答应下来，但紧接着补了一句「不过——」。这个停顿后面跟着的就是客户端自己要承担的工作：先把大文件切分成数据块，再交给 HDFS 存储，图上的原话是「首先，我把这个大文件切分成块」。

因此切分的执行者是客户端，不是 NameNode。这一点在概念题里经常被反过来问。NameNode 在这个过程中只接收切分结果、把块与文件的对应关系登记进元数据，并不参与文件的物理切分。

切分的规则是按块大小顺序切，最后一块允许不满。以图上 200MB 的文件、128MB 的块大小为例，结果是两个块：一个是完整的 128MB，另一个是剩下的 72MB。这也是块的一个基本性质——除文件末尾的块之外，其余各块都是满的。

3. 客户端必须知道的两个参数

图上客户端有一句话：「一个好的客户端总是知道这两件事。」它身前摆着两个方框，写着这两个参数。

第一个是 BLOCKSIZE，也就是块大小，含义是大文件被切成多大的块，通常是 64MB 或 128MB。

第二个是 REPLICATION FACTOR，也就是副本因子，含义是每个块要保存几份，通常是 3。

这两个参数决定了写入的形态：前者决定文件被切成几个块，后者决定每个块被复制到几个 DataNode 上。图侧的手写批注也正好落在这两处，标出「需要设置：块大小、几个备份」，并追问了一句「64MB 或 128MB，为什么是这么大」——这个问题在讲块大小权衡的那一小节回答。

4. 写入时的 DataNode 分配

客户端把文件切分成块之后，写入并不是一次提交整个文件，而是以块为单位逐个进行。图左侧的手写批注把这一点标了出来：开始按 Block 为单位进行写入。因此客户端向 NameNode 发出的第一句话是「请帮我写入一个 128MB 的块，副本数为 3」，申请的对象是第一个块，而不是整个 200MB 的文件。文件包含多少个块，这样的申请就要重复多少轮。

分配 DataNode 是 NameNode 的职责。NameNode 接到申请后的反应是：副本数为 3，那我需要为这个客户端找出三个 DataNode。图右侧的批注把这一步写成一句结论——NameNode 负责分配 DataNode。客户端不能自己指定把块写到哪台机器上，它只能提出要求，落点由 NameNode 决定。

决定之后，NameNode 把三个 DataNode 的地址返回给客户端。图上的原话是「给你，兄弟，三个 DataNode 的地址。我还按与你之间距离由近到远的顺序排好了」。图右侧的批注记录的正是这一步：NameNode 通知客户端三个 DataNode 的位置。客户端回一句「谢谢」，随后才与这三台机器建立连接并写入数据。

这里有一个细节值得单独记住：NameNode 返回的不是一个地址，而是三个候选地址，并且带有排序。排序的依据是节点与客户端之间的距离，由近到远。这样客户端可以从最近的一个开始写，剩下的副本再由已经接收写入的节点继续传给其他节点。这个顺序不是随意排的，它直接影响写入的耗时，跨机架传输要比同机架慢得多。

至于 NameNode 具体依据什么规则挑出这三个 DataNode，这一页没有展开。它的自问自答是「这件事我怎么做呢？以后再告诉你」——答案在紧随其后的那一页给出，也就是下一小节的机架感知写入策略。

课件在这一页的左下角留了一个问题，用红笔写着：「选择哪个 DataNode 存储数据块最优？」其中「最优」二字下面还划了着重线。这个问题不是没有答案，课件随后专门用一页正面回答了它。复习时把两页连起来看：一页负责提出问题，一页负责给出规则。

5. 机架感知的写入策略

分配 DataNode 的具体规则由机架感知策略给出，这一小节回答的正是上一小节被推迟的那个问题。策略的前提是集群的组织方式：集群按机架和节点两级组织，一个集群分成若干个机架，每个机架上有多台 DataNode。同一机架内的节点之间传输带宽高，跨机架通信则要经过机架之间的交换设备，代价更高。图左侧的批注把这个前提标了出来：集群按机架和节点进行组织。

第一个副本的位置最简单。如果发起写入的客户端本身是集群的一员，就选客户端所在的节点存放第一个副本；如果客户端不在集群内，就随机挑一个 DataNode。图右侧的批注记录了这条规则：第 1 个块尽量选择与 Client 同一个服务器，或随机。这也解释了上一小节返回的地址为什么要按距离排序——排在最近的就是客户端自己那台机器，它与客户端的距离为零。

第 2、3 个副本另选机架：先挑一个与第一个副本所在机架不同的机架，再在这个机架上选两台不同的 DataNode。图右下角的批注写的就是这条——后 2 个副本另选机架。

如果副本因子大于 3，后续的副本随机选节点，但要满足两个条件：每台 DataNode 上最多存放同一数据块的一个副本，每个机架上最多存放两个副本。图左下角的批注把这两条归纳成一句话——1 个 DN 最多一个备份，每个机架最多两个。这里有一个措辞需要留意：批注里写的是「Block」，但四格图的四个格子标题写的都是副本的位置（replica location），这套策略讨论的是同一个数据块的各个副本放在哪里，而不是文件的不同块怎么分布，两种说法不要混。

按默认的三个副本算，最终的分布形态是：一个机架放一份，另一个机架放两份，三个副本只落在两个机架上。这样放置兼顾了性能与容错——写入时副本在机架内部可以走高速链路传递；任何一个机架整体掉线，另一个机架上至少还有一份副本可读。判断题若问「三个副本分别放在三个不同的机架上」，按这套策略应判错误。

6. 块大小取决于文件规模

块的大小需要在两个方向之间权衡。结论可以直接记住：文件大，块适合设置得大一点；文件小，块不要设置得太大。

块设得偏大，好处是块的数量少，NameNode 需要维护的元数据少，寻址开销在总时间里的占比低，顺序读写的吞吐量高。代价是单个块的处理时间变长，一个作业中并行的任务数变少，只要少数几个块拖了后腿，整个作业的完成时间就被拉长；块一旦损坏，重新复制的代价也更大。

块设得偏小，好处是并行粒度细，数据分布和任务划分都更均匀。代价是块的数量成倍增加，NameNode 的内存压力和寻址开销随之上升，大量时间花在定位数据上而不是读取数据上。

把这两个方面放到文件规模上看就清楚了。处理大文件时，文件本身会包含很多个块，把块设大一些能够显著减少块的总数和元数据负担，同时充分利用顺序读写的优势。处理小文件时，一个文件本来就填不满一个块，块设得再大也用不满，反而降低了调度粒度，不如取较小的块，让数据分布和任务划分都更细。

7. 默认值

Hadoop 1.x 的默认块大小是 64MB，Hadoop 2.x 及之后的版本默认是 128MB，具体数值由配置项 dfs.blocksize 控制。默认值本身就是权衡的结果，处在「便于并行」和「减少元数据」之间。前面留下的那个追问——为什么是这么大——答案就在这里：这个尺寸大到可以让块数足够少、顺序读写足够连续，又小到让一个作业能切出足够多的任务并行推进。

8. 小文件问题

HDFS 不擅长处理海量小文件。原因是每个文件、每个块在 NameNode 中都要占用一份元数据，量级大约在 150 字节，小文件数量上亿时，元数据占用会把 NameNode 的内存耗尽。此外，读取一个小文件就要启动一个 map 任务，任务启动和调度的时间开销往往超过了读取数据本身的时间。

常见的应对思路是把小文件合并之后统一存储，让一个块容纳多个小文件，或者把小文件打包成顺序文件、归档文件等容器格式再上传。考试如果问到，答出「合并存储、减少 NameNode 元数据压力、避免为每个小文件单独启动任务」这个方向即可。

9. 副本与节点分工

每个块默认保存三份副本，分布在不同 DataNode 上，并且尽量分散到不同的机架。具体怎么分散，由机架感知的写入策略决定，规则见前面讲机架感知的那一小节。这样既能容忍单个节点故障，也能容忍整个机架掉线。副本因子这个参数之所以要按文件设置而不是写死，也是因为可靠性与存储开销之间存在取舍：副本多则更可靠，代价是同一份数据占用多份空间。

客户端读取文件时的顺序是，先向 NameNode 询问目标块的位置，再直接与对应的 DataNode 建立连接读取数据；写数据时同理，NameNode 只给出该往哪些节点写，数据并不经过它转发。客户端、NameNode 与 DataNode 三者的完整分工见下一节。

九、HDFS 的节点分工

课件用三页内容讲这一部分：一页把集群里的三种角色摆了出来，之后一页专门展开 NameNode，再一页专门展开 DataNode。这一节把三页合并，复习时对着图说清楚每种角色的数量、职责，以及 NameNode 和 DataNode 各自在管什么。

1. 客户端（Client）

客户端是用户提交读写请求的入口。用户通过客户端向 HDFS 发起读数据或写数据的操作，课件里它说的是「人们坐在我面前，让我读数据、写数据」。客户端本身不存储数据，它承担的是用户与文件系统之间的接口角色。客户端可以有很多个，任何一台能够访问集群的机器都可以充当客户端。

2. NameNode 的定位

NameNode 是主节点，课件中它的原话是「我只有一个」，并且「我协调这里周围的一切」。它的职责是管理文件系统的命名空间，记录文件被切分成哪些块、每个块存放在哪些 DataNode 上，并在节点增减时维护这份映射关系。它保存的是元数据，不存储实际的数据内容。

需要单独记住的是，NameNode 只有一个，意味着它是整个 HDFS 的单点。一旦 NameNode 失效，客户端就无从得知数据块的位置，整个文件系统在逻辑上变得不可访问。后续版本为此引入了 SecondaryNameNode 以及 HA 高可用机制来做缓解，这也是这一节最容易出延伸题的地方。

3. NameNode 的三项职责

课件把 NameNode 的职责列成三条，并且在左侧架构图上用 ①②③ 标出了各自对应的位置。复习时要把文字条目和编号对上号，考试问「NameNode 负责什么」时按这三条答，条理最清楚。

1. 管理元数据，对应图上的 ①。这是 NameNode 最核心的职责。它保存和管理整个文件系统的命名空间，其中包括目录树，以及文件和目录的元数据；同时还要保存并构造「文件、数据块、数据块所在 DataNode」三者之间的对应关系。图上 ① 号标在 NameNode 与上方 Metadata 方框之间的连线上，表示这份账目由 NameNode 统一持有和维护。

2. 与客户端交互，进行文件操作与元数据查询，对应图上的 ②。图上 Client 与 NameNode 之间画的是双向箭头，② 号就落在这条箭头上。客户端要读一个文件时，先向 NameNode 提问：这个文件被切成了哪些块、这些块分别在哪些 DataNode 上。NameNode 只回答位置，不承担数据内容的实际传输，真正把数据读出来的是客户端与 DataNode 之间的连接。写文件的过程同理，先由 NameNode 决定数据应当往哪里放。

3. 接收 DataNode 的数据块报告，更新元数据，分配数据存储节点，对应图上的 ③。图上半部分 NameNode 用虚线箭头指向下方三个 DataNode，③ 号就标在这条线上。DataNode 会定期向 NameNode 汇报自己保存了哪些数据块、运行是否正常，NameNode 据此更新元数据中记录的块位置；当有新的数据写入时，也是由 NameNode 来决定这些块分配到哪些 DataNode 上。图中每个 DataNode 方框内画着若干块编号（3、5、1、4 等），表示数据块以编号标识、分散保存在不同节点上。

三条职责可以按「管账、答问、派活」来记：① 是管账，把命名空间和块位置这本账维护清楚；② 是答问，向客户端回答数据在哪里；③ 是派活，把块安排到具体节点并收集节点反馈。记住这个口诀，答题时三条不会漏。

4. 元数据里记录了什么

图左侧的 Metadata 方框给出了元数据的具体样子：框内标注的是 Name、replicas 等条目，下面两行是文件与数据块的对应关系，分别是 /home/foo/data1 → 2, 3, ... 与 /home/foo/data2 → 1, 4, ...。

这两行是理解元数据的关键。它们表示，对于文件 /home/foo/data1，元数据记下的是「它由 2 号、3 号等数据块组成」，而记录的内容是块编号，不是块里装的数据。文件名到块编号的映射，再加上每个块落在哪个 DataNode 上，合起来就是 NameNode 手里的全部账目。

对照这个例子，可以把几处容易混的说法一次说清楚。其一，NameNode 存的是元数据，数据块的内容存在 DataNode 上，这正是「NameNode 保存着所有文件的实际内容」这类判断题判为错误的依据。其二，账目和实物分开存放，于是 NameNode 一旦失效，DataNode 上的数据其实都还在，但已经没有谁说得清哪一块属于哪个文件，整个文件系统因此在逻辑上不可访问，这就是它被称为单点的原因。其三，replicas 出现在元数据中，说明副本数是文件一级的属性，读取时要查的是「这个块有几份、分别在哪几个节点」。

5. DataNode 的定位

DataNode 是工作节点，课件中它的原话是「我们存储数据，我们有很多个，有时甚至上千个」。它的定位是数据的实际存储节点：文件被切成数据块之后，这些块真正落盘保存的地方就在 DataNode 上。客户端读取数据时，NameNode 只负责回答数据在哪里，真正的数据传输直接发生在客户端与 DataNode 之间。DataNode 的数量可以很多，集群的存储容量与读取吞吐主要靠增加 DataNode 来横向扩展，这一点与 NameNode 只能有一个恰好形成对照。

6. DataNode 的四项职责

课件把 DataNode 的职责列成四条，并且在架构图上用 ①②③④ 标出了各自对应的位置。与 NameNode 那一页的处理方式相同，复习时要把文字条目和图上编号对上号，考试问到 DataNode 负责什么时按这四条答。

1. 数据存储节点，这是最基础的一条。图中每个 DataNode 方框里画着若干带编号的小方块（3、5、1、4 等），表示数据块以编号标识、分散保存在各个节点上，全集群的存储容量由这些节点累加而成。

2. 与客户端交互，进行数据读写，对应图上的 ① 与 ②。图上 ① 标在左侧 Client 指向左侧 DataNode 的箭头上，② 标在右侧 Client 指向右侧 DataNode 的箭头上。两个编号分处两条连线，说的是同一件事：客户端写数据时把块写进 DataNode，读数据时从 DataNode 把块取出来，两条链路都是客户端与 DataNode 直接相连。上一页说 NameNode「只回答位置，不碰数据」，依据就在这里——读写链路的箭头画在 Client 与 DataNode 之间，而没有画在 Client 与 NameNode 之间。

3. 数据节点之间的交互，文件分割为数据块，冗余备份存储在多个 DataNode 中，对应图上的 ③。③ 号标在横向连接各 DataNode 的虚线上。这一条讲的是副本的传递：一个块写进来之后，接收写入的节点会把副本继续传给其他节点，形成节点之间的数据流动。图中编号为 3 的块同时出现在三个 DataNode 方框里，编号为 4 的块也出现多次，表达的正是同一份数据在不同节点上各存一份。副本分散存放的直接意义是容错，任何一个 DataNode 失效，都还有别的节点留着同一份数据。

4. 向 NameNode 定期报告数据块存储情况，对应图上的 ④。④ 号标在下方 DataNode 指向上方 NameNode 的虚线上。DataNode 会定期汇报自己保存了哪些数据块、运行状态是否正常，NameNode 据此维护和更新元数据。需要区分的是，这条汇报与第 2 条中客户端向 NameNode 的查询是两回事：前者是节点自动进行的例行上报，后者是用户操作流程的组成部分。

四条职责可以按「存数据、通客户端、传副本、报状态」四组词来记，后三条分别落在 ①②、③、④ 三处连线上，位置和编号不会串。

7. 数据块的副本与冗余备份

课件第三条职责里提到「文件分割为数据块，冗余备份存储在多个 DN 中」，这句话把块机制和副本机制连在了一起。块机制解决的是大文件如何切分，副本机制解决的是切分之后放在哪里、放几份。

这两件事需要合起来理解。块切得再细，如果同一个块只放在一个节点上，那个节点一旦失效，数据就没有了；副本的做法是让同一个块在多个 DataNode 上各存一份，默认三份，写入时由节点之间依次传递，读取时客户端可以选择较近或较空闲的一份。图里编号为 3 与 4 的块都重复出现在多个节点中，正是这种分布方式的示意。

副本数量记录在文件的元数据里，也就是上一页 Metadata 方框中的 replicas 一项，因此它是可以按文件调整的，并不是一个固定常数。副本带来的是可靠性，代价是同样的数据要占用多份存储空间，这个取舍在回答方案设计题时值得写出来。

8. 三者关系

一句话概括：客户端发起请求，NameNode 告诉它数据在哪里，DataNode 把数据交出来。数量关系记成「客户端多个，NameNode 唯一，DataNode 众多」。这一句是理解后续设计取舍的起点——NameNode 之所以是瓶颈、DataNode 之所以可以横向扩展，根源都在这里。

9. 课堂上圈注过的记号

NameNode 那一页在课堂上是带着标注讲的：NameNode 被红笔圈出来，旁边写了 boss，并且把「我只有一个」和「我协调这里周围的一切」两句划了线。客户端那一句（人们坐在我面前，让我读写数据）和 DataNode 那一句（我们存储数据，有很多个）没有划线，属于看懂图就能理解的部分。

记号指向的考点因此很明确：考试一旦涉及节点分工，NameNode 是重点，答题时「唯一」和「协调全局」这两个词必须写出来，并能顺着说到它为什么是单点、为什么成为系统的瓶颈。客户端只要说清「入口」这个定位即可。

DataNode 这一页没有红笔圈注，重点由课件自身的编号给出。四条职责分别落在 ①②③④ 四处连线上，编号本身就是提示：①② 在客户端与 DataNode 之间，③ 在 DataNode 彼此之间，④ 从 DataNode 指向 NameNode。换句话说，前两条讲的是读写通道，后两条讲的是副本传递与状态汇报。图上另有一条红色弧线把中间节点与左侧节点连起来，与 ③ 号虚线一并表示副本在节点之间的传递方向。

把两页的记号放在一起看，这一节的答题口径就清楚了：NameNode 的关键词是「唯一」与「协调」，DataNode 的关键词是「实际存储」与「副本传递」，客户端的关键词是「入口」。

十、如何监测网络错误

前面几节讲的都是正常情况下的读写流程，这一节看的是出问题的时候：数据发出去之后，发送方凭什么判断对方到底收到没有。课件这一页的大标题是「如何监测网络错误？」，方框内的标题是 DETECTION #2: NETWORK FAILURES，也就是分布式系统故障检测机制中的第二种——网络故障的检测。

1. 检测机制：每次发送数据都要求一次 ACK 确认

图上第一句结论是「每当数据被发送出去，接收方都会回送一个 ACK」。画面里 Data 用一条实线箭头从左侧主机指向右侧节点，ACK 用一条虚线箭头反着回到左侧，一往一返，恰好构成一次完整的传输。ACK 是确认应答的缩写，在这个机制里承担的角色是回执。

课件在「Whenever data is sent」这一句下面用红笔划了线，落点在「每次发送」上，说明这一页的支点就是这条对应关系：有发送，就必须有一次回来。

这条机制之所以必要，是因为发送方看不见对方。它只能确认自己把数据送进了网络，无法确认数据究竟有没有到达对端，所以必须由接收方回送一个信号，发送方才有依据判断这次传输是否成功。

2. 判定规则：重试若干次仍未收到 ACK 的后果

图上的第二句结论说，如果一直没有收到 ACK（在若干次重试之后），发送方就认为那台主机已经死掉，或者是网络发生了故障。这句话有两个地方必须写准。

1. 判定条件是「重试若干次之后仍未收到」，而不是「一次没收到就判定」。网络上偶发的丢包和短暂的拥塞都会让某一次 ACK 迟到或者丢失，如果一次没有收到就把对端判死，正常节点会被反复误判，系统把大量精力耗在重传和恢复上。重试的作用正是把这些偶发情形排除掉，只有连续多次都没有应答，才当成真正的故障。

2. 判定结果是发送方的推断，包含两种可能。它掌握的事实只有一个——对方没有应答；至于对方是进程已经结束、机器已经断电，还是链路中断，它区分不了，因此课件的措辞是「认为主机已死，或者网络发生了故障」。答题时两种可能要一并写出，不能只写其中一种，也不宜写成「确认主机已经死掉」。

3. 与 DataNode 定期上报的区别

这套 ACK 机制容易和前面节点分工那一节里 DataNode 的最后一项职责混在一起。两者的分工可以分三句话理清。

1. 链路位置不同。ACK 发生在一次数据传递的双方之间，属于数据通道上的确认；DataNode 的定期上报发生在 DataNode 与 NameNode 之间，属于控制通道上的汇报。

2. 触发方式不同。ACK 由每一次发送触发，发起者是发送方，一问一答；定期上报按时间周期自动进行，发起者是 DataNode，不需要谁去追问。

3. 判据的用法相同。两者都靠「对方有没有按时回话」来判断对方还在不在、通不通：ACK 用来判断这一份数据有没有送到，上报用来判断这个节点还活着没有、手里有哪些数据块。收不到应答，就是故障的信号。

十一、HDFS 的命令行操作（Shell）

课件用一页列出了 HDFS 的常用命令。这一页是操作层面的内容，要记的是命令格式加一批命令的用途，考试里多以选择、填空和简答的形式出现。

1. 命令格式

HDFS 的命令行格式是 hadoop fs -cmd <args>，由三段构成。

1. hadoop fs 是固定的调用前缀，表示调用 Hadoop 的文件系统工具，所有命令都以它开头。

2. -cmd 是具体的指令内容，前面带一个连字符，例如 -ls、-copyFromLocal。课件对它的定义就是「具体指令内容」。

3. <args> 是一系列可变的参数，通常包含路径、权限值、目标位置等。尖括号本身就是「此处要填入内容」的写法，同一组参数换一换，同一条命令就作用于另一个文件或目录。

三段连起来读是：用 Hadoop 的文件系统工具，执行某一个具体指令，并把一批参数交给它。

2. 常用命令及其用途

课件一共列了 14 条命令，按用途分成三组更好记。第一组是查看与列目录。

1. cat，显示非压缩文件的内容，示例 hadoop fs -cat hdfs://nn1.exp.com/file1。限定词「非压缩」要注意，压缩文件直接查看不会得到可读内容。

2. ls，列出文件和子目录，示例 hadoop fs -ls /usr/hadoop/file1。

3. tail，显示文件的最后 1KB 数据，示例 hadoop fs -tail /usr/hadoop/file1。它只看结尾而不是全文，适合快速确认文件有没有写进去。

第二组是本地与 HDFS 之间的传输。课件用红色标出的三条命令都在这组。

4. copyFromLocal，从本地复制文件到 HDFS 文件系统中，示例 hadoop fs -copyFromLocal localf1 /usr/hadoop/file1。方向是本地到 HDFS，操作完成后本地的源文件仍然保留。

5. copyToLocal，从 HDFS 复制文件到本地，示例 hadoop fs -copyToLocal /usr/hadoop/file1 localf1。方向与上一条正好相反。

6. moveFromLocal，将文件或目录从本地移动到 HDFS，示例 hadoop fs -moveFromLocal localf1 /usr/hadoop/file1。方向与 copyFromLocal 相同，区别在于是「移动」：写进 HDFS 之后，本地的源文件不再保留。

7. get，从 HDFS 复制文件到本地，示例 hadoop fs -get /usr/hadoop/file1 localf1。用途与 copyToLocal 相同。

8. put，把文件或目录从本地送入 HDFS，示例 hadoop fs -put localfile1 /usr/hadoop/file1。课件对这一条的说明写作「将文件或目录从本地移动复制 HDFS」，按它与 copyFromLocal 的对应关系看，作用就是本地向 HDFS 的上传。

第三组是 HDFS 内部的文件与目录管理。

9. chmod，改变文件或目录的访问权限，示例 hadoop fs -chmod 777 hdfs://nn1.exp.com/file1。777 是权限值的写法。

10. chown，变更文件或目录的所有者，示例 hadoop fs -chown user1 hdfs://nn1.exp.com/file1。

11. cp，复制文件或目录，示例 hadoop fs -cp /usr/hadoop/file1 /usr/hadoop/file2。源和目标都在 HDFS 上，是文件系统内部的复制。

12. mkdir，创建目录，示例 hadoop fs -mkdir /usr/hadoop/dir2。

13. mv，将文件或目录的源路径移动到目的路径，示例 hadoop fs -mv /usr/hadoop/file1 /usr/hadoop/file2。与 cp 一样属于 HDFS 内部的操作。

14. rm，删除文件或空目录，示例 hadoop fs -rm /usr/hadoop/dir1。课件明确写到只能删空目录，目录里还有文件时这条命令不能直接把它删掉。

3. 命令之间容易混的两处

1. 方向。copyFromLocal 与 put 都是本地到 HDFS，copyToLocal 与 get 都是 HDFS 到本地，两组的差别只在命名上，方向不会随名字改变。cp 与 mv 的源和目标都写在 HDFS 路径上，属于文件系统内部的操作，不能用来在本地和 HDFS 之间搬运数据。

2. 源文件是否保留。moveFromLocal 与 mv 都是移动，操作完成后源处的文件不再存在；copyFromLocal、copyToLocal 与 cp 都是复制，源文件保留。课件用红色标出的三条命令之所以值得单独记，正因为它们同时体现了方向和保留与否这两件事：一条上行且保留源文件，一条下行，一条上行但不保留源文件。

4. 路径的两种写法

课件的示例里出现了两种路径。一种是 hdfs://nn1.exp.com/file1，以 hdfs:// 开头，后面接 NameNode 所在的主机名与文件路径，属于完整写法；另一种是 /usr/hadoop/file1，用斜杠开头的绝对路径直接给出位置，省略了协议与主机部分。两种写法指向的都是 HDFS 上的文件，复习时能认出来即可。

十二、智能应用部分

课程目标里提到的 RAG 架构和 RWKV 大语言模型属于应用层内容。RAG 的基本思路是，在大模型生成回答之前，先从外部知识库中检索与问题相关的内容，把检索结果作为上下文一并交给模型，以此缓解模型知识过时和凭空编造的问题。课程给出的示例是江西文旅智能导游，知识库来自景点资料，模型负责把检索到的内容组织成自然语言的回答。

这部分内容如果出现在试卷上，多半以概念解释或方案设计的形式考查，不需要记忆模型的内部细节和参数规模。
